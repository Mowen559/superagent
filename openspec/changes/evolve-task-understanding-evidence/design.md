# Design

## Context

基线为 `feature/ai-core-workbench@80b1f75`。已有规范化别名/参数、审批工作区策略、追踪、四阶段指导、思考等级、卡死检测和角色路由，但认知仍只消费状态与风险；清单完成存在两个快捷成功出口。旧功能分支提供独立需求契约和收据机制，可作为适配来源，不整体合并旧提示词或旧主架构。

## Goals / Non-Goals

**Goals:** 保留当前分支接口与机制；共享当前 Run 的计划状态；使修订、证据新鲜度和所有完成路径服从同一确定性门禁；实际上下文优先于假定框架。

**Non-Goals:** 跨进程规划恢复、自动授权、强制多智能体、额外后台模型调用、自然语言业务语义完备性证明及五项领域 Golden Evals 总脚本。本轮不宣称整体效果提升百分比。

## Decisions

1. 复用 `TaskContract`、`TaskProgress`、`PlanRevision` 独立模块，在现有装配处注册 `plan_task`、`revise_task_plan`、`update_task_progress`。采用每 Run 独享的共享状态，避免工具与认知维护副本。Schema 与运行时共用限制：12 步、12 条成功条件、16 条约束、8 个问题、规范化 JSON 12,000 字符；收据元数据缓存 256，每个绑定最多 8 项。
2. 修订在副本上合并并拓扑校验，一次提交；省略字段和原依赖保留。变更步骤与后续依赖需要新代次证据，追加要求重开 Verify。完整替换清空绑定，不能通过静默删减条款规避预算。
3. 在当前 Gateway 的别名和参数归一化之后判定进程结果、验证命令与返回状态，保留原有策略、审批、诊断与压缩。不能用风险枚举或普通 `Ok` 推断质量验证。工作区变化或修订重开验证会更新循环保护代次。
4. 顺序、并行分支都传完整收据。RunPlan 的 Inspect/Act/Verify 决定阶段，TaskProgress 决定声明子目标闭合；补充 DoD 门禁不能扩大一次复核预算。三个结束出口共享决定，Blocked 必须记录失败并返回错误，不能学习成功经验。
5. 保留当前分支思考等级、追踪、角色路由和卡死检测；阶段投影由 RunPlan 的真实证据产生。去除泛用内核中的特定爬虫、Java 规则，按真实工作区资料调查；用户尚未决定且影响行为的选择仍可询问。
6. 回滚后保留原计划条款，清空绑定和证据缓存，重置阶段与补充门禁，避免工作区版本已变但旧收据仍有效。仅保留历史日志，不将其自动恢复成完成状态。
7. 使用显式评测 example，真实模式固定配置快照，默认离线。保留模型身份、夹具指纹和用量；以确定性测试验证状态规则，不把合成结果当作真实任务成功率。

## Risks / Trade-offs

- 保守质量命令识别可能拒绝非标准脚本 → 明确失败/缺口，后续通过有断言的契约扩展，不随意放行。
- 收据类型匹配不等于业务语义通过 → 维持 Experimental，文档明确缺少需求语义全覆盖证明。
- 旧代码移植可能覆盖新安全与追踪功能 → 按文件差异适配，保留分支新增回归，检查所有结束出口与归一化调用。
- 长计划与重复上下文增加用量 → 硬预算与明确截断，记录总用量，不将输出减少等同于效率改善。

## Migration Plan

先补行为规范，再适配独立模块、上下文、Gateway 和执行器，最后运行默认库回归、入口检查和离线评测。保持现有 HTTP 请求与输出外形，不引入持久化格式迁移。回退代码时保留账本，不关闭既有授权；已回滚的工作区不能复用旧规划进度。
