## Context

业务技能是提示内容与磁盘资源的组合，目录存在不等于业务可用。工作区可能是外部安装目录，技能仍须从运行包发现。当前自动扫描和显式工具各自维护目录、解析和遍历实现，产生不一致。

## Decisions

1. CapabilityScout 提供共享目录发现和技能目录扫描。优先级为工作区、baseline 原工程、显式运行包/用户技能、可执行程序相邻内置技能。同名技能仅保留第一个；目录及文件排序固定。
2. 挂载内容显示 SKILL.md 的绝对路径与资源根。脚本仅从该技能自身 scripts 目录列举，缺失如实报告；调用示例包含路径引号，不能依赖 Cwd。skill_tool 复用相同扫描，read 同时返回原文与可执行指引。
3. 仅支持已有技能使用的常规标量、带引号标量和 YAML `>`/`|` 多行描述，不引入新的解析依赖。
4. 可行性调查必须先读取给定路径、识别技术栈并获取实际接口证据；鉴权失败与不可测项作为调查结论。只有用户要求生成且端到端验证达成才交付可用规则；本机服务依赖明确标记。
5. 修复不扩大权限。Skill read 可通过目录工具读取发现的技能，不让普通 view_file 越出工作区。读技能不修改共享/内置技能。

## Reproduced execution follow-ups

真实 HTTP 重放证明脚本已生成并校验产物，但自定义 validate.cjs 不被质量命令分类器识别，同时 manage_task 文本清单与结构化任务进度给出冲突的完成指令，最终耗尽轮次。修复将允许受限解释器直接运行明确命名的校验脚本获得质量执行收据（仍须真实前台 exit_code=0，仍拒绝复合命令/帮助/后台），并将结构化任务作为执行进度唯一权威；普通单产物不再被强迫建立两套计划。实际业务正确性仍需独立验收。

新增随包 local-app-inspector 技能，将已验证的 DMGHG v1 原生桥接及无界面解码方法作为明确限域的工具资源。它不伪称能调用任意 DLL、不读取用户账号、不支持绕过账户或付费限制；状态写入临时目录，应用安装目录保持只读。

发布构建须将 skills 与 Hub 同包放在 bin/skills；ASAR staging 与独立 zip 均携带资源，否则本地开发可用不能代表安装后可用。

本机服务验证还复现：有效单一模型配置（无 accounts 数组）可供 worker 使用，但 /v1/models 只返回 sources=[] 的静态模型，SDK 全部过滤后把服务误判离线。模型列表增加 configured/configured_default 布尔元数据，仅在 enabled、baseUrl、apiKey、model 完整时标记实际配置模型；不制造账户来源或健康成功。SDK 接受该标记并优先配置默认值，页面采用 SDK 排序，不硬选旧模型。

最终常用端口重放还触发了结构化计划分支：成功的 PowerShell 查询和 Python 探针均为 ProcessControl，TaskProgress 丢弃这些真实结果，模型看不到可引用的 receipt ID。成功且前台 exit_code=0 的 run_command/verify_task_tool 结果可作为 Observation；它们不是 Mutation 或 Verification。此变化只影响证据分类，不改变工具授权。调查 Run 可用这种命令事实推进查验阶段；帮助/版本等信息也只能证明其自身结果，不能证明业务验收。

临时目录测试覆盖 workspace skills、同名优先级、带空格/中文路径、非工作区资源、缺脚本与多行描述。真实 Hub worker 在隔离配置中使用 gemini-3.8-flash-high；保留模型发起的工具调用与独立磁盘检查。指定应用仅以真实接口/桥接回执认定功能，静态规则检查不能证明播放。
