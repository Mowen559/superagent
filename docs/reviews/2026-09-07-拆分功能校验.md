# 拆分前后功能一致性校验

审查日期：2026-09-07。范围：仓库架构文档、当前三个模块的目录拆分、默认 Windows 功能集的生产目标检查和完整库测试。结论不涵盖真实账户登录、所有 Agent CLI 版本、真实 Provider 调用、桌面录屏和全部跨进程恢复场景。

## 1. 结论

**在本次源码对比和已执行测试覆盖范围内，未发现三个模块拆分造成的功能回归。** 拆分前后生产目标默认检查均通过；对双方应用同一项历史测试调用修正后，完整库测试均为 **226 passed / 0 failed / 2 ignored**。测试名映射后，228 项测试的名称集合及结果一致。

**不能据此声明所有功能正常。** 仓库原样的测试构建被一个历史翻译插件测试阻断；无默认 feature 配置存在视觉模块编译问题；真实 OAuth/CLI/Provider 集成未在本轮认证。此次拆分保留了逻辑，但没有完成充分的依赖解耦，且旧架构文档有多处过期结论。

改进设计见 [系统架构设计 v2](../architecture/系统架构设计-v2.md)。原架构文档保留作为历史资料，本轮没有覆盖其中用户未提交的修改。

## 5. 发现的问题及归因

### A. 已修复：历史测试无法编译

`src/services/visual_pipeline/external.rs:335` 的测试仍使用旧签名。影响整个 lib test 目标，使原文档的测试通过结论无法在当前代码原样复现。与三个拆分模块无关，已用最小测试适配修复，前后完整库测试均通过。

### B. 当前阻断：关闭默认 feature 后无法编译

`src/services/visual_pipeline/mod.rs:260` 无条件引用 feature-gated `native_cropper`，同文件 `:276` 使用可选 `image`；`src/routes/vision.rs:109` 在 feature 关闭后留下无法推断类型的空 Vec。上述文件均不属于此次拆分，初始工作区与 HEAD 相同。这与 Cargo 注释中“原生 SDK 可替换且 feature gated”的目标不一致。

建议单独修正条件编译，并在 CI 验证默认组合与明确支持的最小组合。此次未改变生产功能开关。

补充环境事实：基线的额外 no-default 检查复用现有 target 时，`utoipa-swagger-ui` 生成文件仍引用仓库提升前的 `hub-rs/target` 绝对路径，因此在依赖阶段失败。该结果不能作为“基线实跑得到同样 3 个 feature 错误”的证据；归因依据是对应源码与 HEAD 一致。后续最小 feature 验收应使用干净目标目录，避免搬迁前缓存污染。本轮未清理用户构建缓存。

### C. P1：已有登录可靠性与错误脱敏风险

- `cli_auth/server.rs` 的 PKCE callback 等待没有显式截止时间，用户不完成登录可能无限等待。
- `handle_callback` 在 state 校验前消费 oneshot sender；错误 callback 会终结当前尝试。
- Token JSON 解析错误拼接原始响应正文，可能使上游返回的秘密值进入终端错误。
- DeepCloud 登录先打开浏览器再绑定 listener，存在回调早到竞态。

这些函数与拆分前一致，属于**已有风险**，不是拆分回归；本轮没有操作真实账户。建议在 AuthRuntime 内统一事务、超时、回收和脱敏，再用 loopback mock 验证。

### D. P2：拆分扩大了可见范围和重复策略

三个 facade 使用 `pub mod` 与通配 `pub use`，子文件复制导入并使用 `use super::*`。95 个声明存在可见性变化；其中大量私有细节扩大到 crate 可见。Provider 的 15 个常量各有 8 份副本。建议保留原 public facade，内部私有模块、显式导出、按需 `pub(super)` 和单一策略对象。

### E. P2：目录职责与说明不一致

SSE `stream_events` 位于 `run.rs`，不在说明所写的 `interact.rs`；后者负责交互与事件编码。Provider 主体网络执行仍在 `mod.rs`，不是单纯 facade。CLI `server.rs` 包含 Token 交换、打开浏览器和凭据写入，`ui.rs` 也不是纯展示层。建议按状态所有权提取用例，避免将当前拆文件结果标为已完成 DDD 解耦。

## 7. 验收建议

本次拆分可以标记为“默认构建与现有回归测试兼容”，不要标记“所有能力完成认证”。下一步优先顺序：收口重复策略和导出 → 修复 feature 隔离 → Auth/Agent/SSE 的真实边界契约 → 版本化能力认证。架构演进应遵循 v2 的分阶段门禁，每一步保持公共路径、HTTP 数据形态和存储兼容。

复现 AST：安装脚本声明的 Python 依赖后执行 `py -3.12 scripts/audit_module_split.py --baseline <完整提交> --baseline-dir <基线worktree> --output <结果.json>`。默认 Git 模式也可使用 `--baseline`，Windows 环境原生库兼容问题时优先使用 detached worktree。测试应使用独立 app data 与工作目录，前后应用同一测试适配补丁。
