# SuperAgent 第三阶段：增量计划修订

日期：2026-10-29。承接[第二阶段的实测阻点](superagent-task-evidence-and-evals.md)：完整重写计划容易遗漏原要求、清空进度，并消耗轮次纠正字段格式。

## 已接入的行为

共享 AgentLoop 在每次 Run 开始时，将 `revise_task_plan` 与 CognitiveRuntime 绑定到同一个 TaskProgress。修订仅更新内存中的计划；不修改文件、发起模型请求或扩大权限。

假设已有版本 1 的计划，其中导出步骤 ID 为 `export`，新增要求可以这样表达：

```json
{
  "base_revision": 1,
  "append_constraints": ["不得修改 parser.rs", "dry-run 不得写入输出文件"],
  "append_success_criteria": ["dry-run 能预览 report.json 内容"],
  "upsert_steps": [
    {"id": "export", "goal": "导出 report.json，并支持 dry-run 预览"}
  ]
}
```

既有步骤只需提供 ID 和变更字段。省略的验收条件、证据种类和依赖会保留；提供的新依赖与原依赖合并。新步骤必须提供目标和验收条件，选择适当证据种类。该接口不能删除既有验收条件、约束、步骤或前置依赖，也不能改变既有步骤的证据种类。范围需要真正缩减时，应显式审阅并完整替换计划。

运行时会：

1. 核对 `base_revision`，在副本上合并，再检查预算与依赖。
2. 对步骤做稳定的拓扑排序，允许新增步骤成为既有步骤的前置依赖；未知依赖和循环被拒绝。
3. 保留原有要求、未变步骤的进度及已解决问题。
4. 使变更步骤和后续依赖失效；它们不能再引用修订前的旧收据作为新工作证据。
5. 对新增要求或步骤变更作废旧验证，并重开 Run 的 Verify。即使模型没有单独声明验证子目标，也必须重新检查。
6. 一次性提交新版本，返回保留/失效的步骤 ID。重复追加相同内容为空操作，不增加版本。

过期版本、循环、未知依赖、弱化证据种类或超预算修订均不改变原状态。验证上下文改变也会更新工具循环保护的代次，使合法复验不会因旧的重复次数被拦截。完整替换仍清空绑定，且旧验证不能被重新当成有效检查。

以上保证结构、版本和证据时序正确。原计划本身仍由模型编写；保留原计划的文字不等于证明所有用户意图已被正确理解，某次工具结果是否实现了自然语言验收条件仍需真实业务验证。

## 校验反馈与边界

`TaskContract::schema()` 成为初始规划和增量修订的共同边界来源。调整此前过紧的局部限制，同时设置完整计划总预算：

| 项目 | 上限 |
|---|---:|
| 目标解释 | 600 字符 |
| 验收条件 | 12 条，每条 240 字符 |
| 约束 | 16 条，每条 240 字符 |
| 步骤 | 12 个，目标 320 字符、验收 400 字符 |
| 待查问题 | 8 个，每个 320 字符 |
| 规范化完整 JSON | 12,000 字符 |

总预算仍会约束各字段的组合，不能同时无限接近所有局部上限。Schema 给出这些局部限制；运行时另检查总预算与依赖语义。合法的详细内容保持原样，不做静默截断。

字段错误会一次报告多个路径、实际长度和允许范围，例如 `steps[0].goal: got 321 characters; allowed 1..320`。反馈经既有工具失败通道返回，要求一次修正所有列出的字段，禁止靠删除用户要求缩短计划。

## 复测方式

```powershell
cargo run --example task_understanding_eval -- --case steered-log-plan
cargo run --example task_understanding_eval -- --live --case steered-log-plan --model claude-sonnet-4-6 --output outputs/task-understanding-eval-v3-steering.json
```

本轮针对之前耗尽预算的追加约束场景，使用相同夹具、同一模型、温度 0、每请求输出预算设置为 1,536 Token、每组最多 4 轮；两组总计最多 8 次模型请求。Token 实测采用网关返回的用量统计，默认预览不联网。

v3 的 baseline 使用完整替换，enhanced 使用认知指导、主动上下文和增量工具；两组共享当前校验边界。两种配置都通过真实 CognitiveRuntime 观察规划结果，增强组调用实际的共享状态修订工具。规划范围明确为提案，未来步骤不要求在评测中执行。

报告增加增量调用次数和原验收/约束文字保留情况，并保留此前的实际模型身份、Token、轮次、错误轨迹、词面检查和夹具指纹。原文字保留指标是逐字符串核对，不能代替语义覆盖；baseline 重新措辞也可能被标记为未逐字保留。

v3 改变了工具能力、共享校验边界和状态接入，不能把与 v2 的差异全部归因于单一提示词或增量工具。它也不代表真实代码实现成功率或统计上的稳定提升。能力继续保持 Experimental。

## 验证结果

回归覆盖追加要求保留进度、局部步骤字段保留、稳定依赖排序、变更后的新证据、验证失效、过期/循环/超预算修订的原子拒绝，以及 Gateway→修订工具→CognitiveRuntime 的真实门禁连接。

| 检查 | 结果 |
|---|---|
| 库回归 | 384 通过、0 失败、2 忽略、1 排除；排除此前已通过的慢速全项目审查测试 |
| `cargo check --bins --example task_understanding_eval` | 通过 |
| 评测入口构建和定向离线预览 | 通过；离线模式不联网 |
| `git diff --check` | 通过 |

### 真实模型定向结果

实际模型 `anthropic:claude-sonnet-4-6`，配置别名 `claude-sonnet-4-6`，温度 0，请求输出预算 1,536 Token。夹具指纹保持为 `xxh3:d8a7d10c42b16c71`，实际模型身份核对通过。原始报告：[`task-understanding-eval-v3-steering.json`](../../outputs/task-understanding-eval-v3-steering.json)。

| 指标 | 完整替换 baseline | 增量 enhanced |
|---|---:|---:|
| 更新后合法计划 | 已提交 | 已提交 |
| 模型轮次 | 3 | 3 |
| 固定术语检查 | 4/4 | 4/4 |
| 计划校验失败 | 0 | 0 |
| 重读/读取次数 | 5 | 5 |
| 增量工具成功调用 | 0 | 1 |
| 原验收/约束文字逐字保留 | 否（完整重写） | 是 |
| 输入 Token | 11,049 | 16,464 |
| 输出 Token | 4,942 | 3,069 |

增强组确实调用 `revise_task_plan` 接纳 dry-run 与 parser.rs 保护条件，原计划条款保持原样。baseline 也覆盖了固定检查；“未逐字保留”不表示它一定丢失了原需求。

相较 v2 的两组都耗尽 4 轮，本轮两组都在 3 轮完成。共同的边界修正和评测状态接入也有变化，不能把改善全部归因于增量工具。增强组输出 Token 更少，但输入更多，总 Token 没有降低。这只证明该样例中的流程可用和文字保留性质，尚不证明整体效率或真实编码成功率稳定提升。

后续重点是减少重复上下文投影、建立用户要求到验收步骤的语义覆盖检查，并在更多独立任务与重复运行中验证收益；本阶段继续保持 Experimental。
