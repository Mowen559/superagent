# Spec Delta

## Purpose

为复杂需求维护当前执行中的目标、约束、子目标依赖与待查问题，使追加条件不会静默覆盖原要求，并让调查结果和步骤完成具备可审阅、受预算约束的来源与证据。

## ADDED Requirements

### Requirement: 有来源的上下文调查
系统 MUST 使用当前授权工作区内实际存在的规则与资料，保留路径、读取位置和截断事实；待查问题区分工作区、外部资料和用户选择，可调查的事实先通过工具补齐。

#### Scenario: 已有项目说明能回答问题
- **WHEN** 项目资料包含需求涉及的约束
- **THEN** 系统可引用实际读取收据解决调查问题，不得用模型自述代替来源或读取无关进程目录。

### Requirement: 有界需求契约与步骤证据
系统 SHALL 支持当前执行内的目标、验收、约束、依赖步骤与待查问题；步骤完成必须引用本轮已观察到、类型匹配且依赖满足的成功收据。规划、清单和进度操作不能产生执行证据。

#### Scenario: 使用失败或其他执行的收据
- **WHEN** 完成更新引用失败、未知、跨执行、过期或规划操作收据
- **THEN** 更新被拒绝，原步骤状态保持不变。

### Requirement: 原子增量计划修订
系统 MUST 校验基准版本、预算与依赖后一次提交修订，保留未提及条款及未受影响进度；不能通过增量删除原约束或弱化证据类型，受影响步骤及后续依赖需要新证据。

#### Scenario: 追加 dry-run 和文件保护要求
- **WHEN** 用户在执行中追加要求且计划版本匹配
- **THEN** 原要求保留，受影响进度失效并重新验证；重复增量不改变版本。

#### Scenario: 版本冲突、循环或超预算
- **WHEN** 修订不满足版本、依赖或预算约束
- **THEN** 系统明确返回错误，原计划、版本和证据绑定不变，不静默截断要求。

### Requirement: 执行状态隔离
系统 MUST 按本轮执行隔离计划与进度；工作区回滚后保留需求但撤销旧执行证据，不得将会话历史存在解释为规划状态已跨进程恢复。

#### Scenario: 回滚后再次结束
- **WHEN** 工作区已还原到旧版本
- **THEN** 回滚前的修改和验证不能再次证明任务完成，需重新调查、实施和验证。
