# SuperAgent 第二阶段：子目标证据与需求理解评测

日期：2026-10-29。承接[第一阶段](superagent-intelligence-evolution.md)的需求理解、拆解和主动上下文能力。

## 已接入的运行机制

`TaskProgress` 持有当前 Run 的 Task Contract、最多 256 条成功收据元数据、子目标绑定与问题绑定。记录只包含收据 ID、工具名、证据种类、来源类别和工作区代次，不复制工具参数或凭据。近期投影最多显示 12 条事实；已经引用的收据优先保留。

`plan_task` 可为步骤声明 `evidence_kind`：调查使用 `observation`，变更使用 `mutation`，质量检查使用 `verification`，真实用户选择使用 `user_input`。省略时兼容第一阶段的 `observation` 默认值。

新增 `update_task_progress`，在每次 Run 开始时绑定该 Run 的共享进度状态：

```json
{"action":"complete_step","step_id":"inspect","receipt_ids":["call-read-source"]}
```

```json
{"action":"resolve_question","question_index":0,"receipt_ids":["call-read-readme"]}
```

```json
{"action":"status"}
```

收据必须已由实际执行链观察到，并符合种类和来源要求。依赖尚未完成、引用未知/失败/其他 Run 的收据、引用过期验证或来源不符时，工具返回错误。工作区问题要求本地观察，外部资料问题要求网络观察，用户选择要求成功的 `ask_user` 回应且回应非空。

成功规划、Todo 和进度更新不会成为执行证据。新写操作、可能部分写入的失败和失败进程检查会使旧验证失效，依赖该验证的步骤也随之不能计为完成。修改计划会清空绑定；仍有效的已观察事实可重新引用。

两个执行分支把收据送入同一个 CognitiveRuntime。最终答案和 Evolution Report 都检查子目标及待查问题是否仍有缺口。进度不会泄漏到下一次 Run。

明确以“只做规划/只给方案”或 `planning only` 等范围指令开始的请求作为提案处理，支持常见礼貌前缀。此时未来实施步骤保持“未执行”状态，不会为了通过完成门禁而要求越过授权范围实施；现有仓库提案仍须先取得调查证据。出现在修复对象或引用文本内部的“只做规划”字样不触发该模式。

上述门禁核对可验证的执行结构。它仍不能自动判定某次修改是否真正实现了自然语言验收条件，也不能证明模型选择的子目标、证据类型和证据关联在业务语义上正确。

## 可重复的规划评测

运行入口：

```powershell
cargo run --example task_understanding_eval
cargo run --example task_understanding_eval -- --live
```

默认命令只显示离线预算，不联网。`--live` 使用已配置的 Canonical Model Gateway，冻结一次配置快照，温度设为 0，单请求输出不超过 1,536 Token。3 个合成场景分别运行 baseline/enhanced，每条最多 4 次模型请求；最多 24 次模型请求，每批最多 8 个工具调用。Provider 故障或请求超时会停止后续评测。底层仍采用已有有限 Provider Route。

评测不读取真实项目源码、记忆或凭据作为模型上下文，不执行模型建议的代码，只允许读取内置合成文档、提交计划和记录模拟反问。原有网关按既有方式使用账户凭据进行鉴权。

| 场景 | 观察内容 |
|---|---|
| CSV 导入 dry-run | 预览、行号、从文档取得编码约定、避免数据库写入 |
| 离线笔记检索和导出 | 复用 FTS5、导出文件名、既有排序和笔记 ID |
| 追加日志分析约束 | 保留原目标，吸收 dry-run 与受保护文件限制 |

两种配置具有相同工具和可访问的合成资料。baseline 使用简短规划指导，enhanced 额外使用当前 CognitiveRuntime 指导和与生产共用的主动工作区摘录。baseline 不是历史发行版，评测也不代表整个 AgentLoop 的历史版本 A/B。

报告记录实际 Provider/Model 收据、结构合法性、术语覆盖检查、缺失项、无效反问、上下文读取及读取失败、非法工具/计划调用、追加条件后的更新行为、Token、网关成本估计和耗时。记录配置快照中的模型别名、温度、输出预算及合成夹具指纹；每次工具调用保留有界错误轨迹。只有完整的两组请求都具有同一个实际模型的收据，才标记可做同模型比较；规划失败本身不表示使用了不同模型。缺失用量记录不补造 Token。成本为网关估计，0 可能表示缺少价格信息。

术语检查是确定性的词面代理：不能区分所有否定语义或等价表达，不能替代人工审阅和真实实现测试。本阶段保持 `agent.task-understanding = Experimental`。

### 首轮真实模型结果与修订

首轮原型已运行实际模型 `anthropic:claude-sonnet-4-6`。baseline 提交 2/3 份合法最终计划，enhanced 提交 1/3；部分场景耗尽 4 轮预算。没有发生无效反问，但存在计划校验失败和对未提供源码的反复读取，不能据此宣称增强模式更好。

首轮输出保存在 `outputs/task-understanding-eval-initial.json`，其合成资料保存在 `outputs/task-understanding-eval-initial-fixtures.json`。首轮 `same_actual_model` 原型判定额外要求计划成功，因而返回 false；各行实际模型收据相同。已修正此判定，将计划失败和模型身份分开核对。

随后补齐合成 README 指向的源码骨架和构建清单；收紧生产认知指导，要求按可验收结果合并步骤、区分事实与设计假设、把未取得的事实登记为缺口。新版报告增加调用错误轨迹和夹具指纹。两组配置使用同一新版夹具复测；夹具已经改变，不能把跨轮差异全部归因于提示词修改。

### 复测结果

实际模型为 `anthropic:claude-sonnet-4-6`；配置别名 `claude-sonnet-4-6`，温度 0，输出上限 1,536 Token。两组均使用夹具指纹 `xxh3:d8a7d10c42b16c71`；实际模型身份核对通过。原始报告：[`task-understanding-eval-v2.json`](../../outputs/task-understanding-eval-v2.json)。

| 场景 | baseline | enhanced |
|---|---|---|
| CSV 导入 | 提交计划，术语 3/4，4 轮 | 提交计划，术语 3/4，3 轮 |
| 离线笔记 | 提交计划，术语 5/5，3 轮 | 提交计划，术语 3/5，3 轮 |
| 追加日志约束 | 4 轮耗尽，未提交符合新条件的最终计划 | 4 轮耗尽，未提交符合新条件的最终计划 |

两组均提交 2/3 份合法最终计划，无无效反问、无缺失文件读取。baseline 总计输入 32,735、输出 11,196 Token；enhanced 输入 41,456、输出 9,340 Token。这个小样本没有证明增强模式稳定优于基线，且增强指导增加了输入开销。

人工复核发现：离线笔记 enhanced 的“术语 3/5”属于代理指标漏判。计划明确包含“不发出网络请求”“id 字段保留在序列化输出中”，但别名表没有识别这些表达；不能把该分数当作实际遗漏离线或 ID 要求。报告保留原始分数，未为了得到更高结果改写规则。

错误轨迹定位到具体摩擦：模型多次超过成功条件/约束条数上限或步骤目标长度上限，修正结构消耗额外轮次。追加条件后 baseline 又超过约束条数上限；enhanced 则重新读源码直到预算耗尽。源码骨架中的 `todo!()` 还可能诱导模型额外规划补全既有实现，说明这些合成场景也需要继续校准。

下一阶段优先处理可保留既有目标的增量计划修订、结构化输出的校验反馈，以及带人工审阅的语义覆盖评测。继续禁止把词面分数或少量合成规划样例宣传为真实编码成功率提升。
